Base URL and authentication

Set these once and every example on this page runs as written.

# the admin host — the Cloudflare tunnel hostname in the current setup
BASE=https://<your-admin-host>
AUTH="Authorization: Bearer $ADMIN_TOKEN"

Every endpoint requires the bearer header except the three panel pages. There is one shared token — no user accounts, no roles, no per-person access. Anyone holding it can read every customer's name, number and full chat history.

Authorization: Bearer <ADMIN_TOKEN>

Token comparison is constant-time and a missing header is rejected the same way a wrong one is, so the endpoint gives nothing away to a guesser.

Error responses

Every failure is a JSON body with a single detail string. No error codes to map.

StatusWhenBody
400Validation failed{"detail": "<what was wrong, naming the field>"}
401Header missing or wrong{"detail": "Invalid or missing admin token."}
404No such record, or not applicable{"detail": "…"}
502Gemini unreachable (knowledge base only){"detail": "…"}
503Redis unavailable (session reset only){"detail": "Redis unavailable: …"}
503ADMIN_TOKEN unset on the server{"detail": "Admin panel is disabled (ADMIN_TOKEN is not set)."}

An unset token disables the panel, it does not open it. Every request gets 503 until ADMIN_TOKEN is set — there is no state in which the API answers without one.

Operations

Is the bot alive, and how do I unstick one customer.

GET/admin/healthNo auth

Liveness only — deliberately dependency-free, so it still answers when Redis and the CRM are down. Point your uptime monitor here; use the status endpoint for real health.

curl -s "$BASE/admin/health"

{"status": "ok"}
GET/admin/api/status

One rolled-up verdict over six checks. No parameters. Live probes are cached for 60 seconds so polling this page cannot hammer the CRM.

curl -s -H "$AUTH" "$BASE/admin/api/status"
{
  "status": "degraded",
  "checked_at": "2026-08-18T09:14:02Z",
  "checks": [
    {"name": "Redis",       "status": "ok",       "detail": "Connected (2 ms)"},
    {"name": "Worker",      "status": "ok",       "detail": "1 worker, last seen 4s ago"},
    {"name": "Queue",       "status": "degraded", "detail": "47 messages waiting, 3 failed"},
    {"name": "Gemini key",  "status": "ok",       "detail": "Runtime key active"},
    {"name": "JAM CRM",     "status": "ok",       "detail": "Reachable (310 ms)"},
    {"name": "JAM dispose", "status": "down",     "detail": "HTTP 502 (cached 12s ago)"}
  ]
}

Fields

FieldMeaning
statusok / degraded / down — the worst individual check
checked_atUTC, ISO 8601, Z suffix
checks[].nameFixed set — always these six, always this order
checks[].detailHuman-readable. Reused probes append (cached Ns ago)

What turns each check red or amber

Checkdowndegraded
Redisunreachable—
Workernone registeredheartbeat older than 480s
Queue—depth over ADMIN_QUEUE_WARN_DEPTH (default 20), or any failed jobs
Gemini key—not configured
JAM CRM / dispose—connection failure or 5xx

Absence is not a fault. A dependency that isn't configured reports ok with "Not configured". When Redis is down, Worker and Queue report down with "Unknown — Redis unreachable", because their true state cannot be known from here.

A 4xx from the CRM counts as reachable — the check proves the host answers, not that the credentials are right.

POST/admin/api/session/reset

Hard-resets one customer. Their next WhatsApp message starts from language selection — language, captured answers, confirmed dealer and brochures-already-sent are all cleared.

Request body

FieldTypeNotes
mobilestringrequiredNon-blank; whitespace trimmed. Use the format the CRM sends, normally +91…
 
curl -s -X POST -H "$AUTH" -H "Content-Type: application/json" \
  -d '{"mobile":"+919371062202"}' "$BASE/admin/api/session/reset"

{"mobile": "+919371062202", "cleared": true}

cleared is false when there was nothing to clear. Both are success. Deduplication keys are left alone — they're keyed per message, not per customer.

Errors — 400 blank or missing mobile; 503 Redis unavailable.

Conversations

Every row is one turn — a customer message or a bot reply — not a whole conversation. Turns are stored the moment they happen, so this is the record of what the bot actually said.

count is the total matching the filter, not the page size — so pagination is Math.ceil(count / limit). items is one page, ordered oldest first within the page, while pages walk backwards from the newest: offset=0 is the most recent page and reads top-to-bottom like a transcript.

role is user or assistant. On a user turn, latency_ms, model, citations and the token counts are empty — they belong to the assistant turn.

Examples

# everything this customer ever said, across all their sessions
curl -s -H "$AUTH" "$BASE/admin/api/interactions?mobile=%2B919371062202"

# what still needs a human
curl -s -H "$AUTH" "$BASE/admin/api/interactions?needs_review=true&limit=50"

# find a phrase
curl -s -H "$AUTH" "$BASE/admin/api/interactions?search=EMI"

Turns recorded before the mobile column shipped have mobile: "" and cannot be found by number. There is no backfill — for those, search by session or by phrase.

GET/admin/api/interactions/{session}

One conversation in full, oldest turn first, up to 500 turns.

curl -s -H "$AUTH" "$BASE/admin/api/interactions/client-e622c23876cc45a"

{
  "session": "client-e622c23876cc45a",
  "count": 12,
  "items": [ /* same shape as the search endpoint */ ]
}

404 when the session has no turns.

A session is not a customer. Someone who comes back after their 1-hour session lapses gets a brand-new session id. To see everything one person ever said, search by mobile instead.

POST/admin/api/interactions/{id}/review

Mark one flagged turn as handled. {id} is the numeric id from the search endpoint. The body is optional — {} is valid.

FieldTypeNotes
notestringoptionalTrimmed. Defaults to ""
 
curl -s -X POST -H "$AUTH" -H "Content-Type: application/json" \
  -d '{"note":"dealer called back"}' "$BASE/admin/api/interactions/4101/review"

{"id": 4101, "reviewed": true, "note": "dealer called back"}

404 here is normal, not an error to surface loudly. It means the turn isn't awaiting review — either never flagged, or somebody already claimed it. That's deliberate, so two people can't both work the same item.

Media

data/media is a shared volume: the admin container writes to it, and the media host serves the same directory read-only at /media/. Publishing is a file write — no CDN account, no third party, no long-running job.

The two kinds

kindDirectoryAcceptsLimitUsed for
brochuresdata/media/brochures.pdf25 MBProduct brochures, warranty and PMS PDFs
imagesdata/media/share_location.jpg .jpeg .png5 MBThe how-to-share-location cards

Any other {kind} returns 404.

Uploading does not change what the bot sends. Publishing a draft must never start delivering it — so after upload, point documents.<product>.brochure or share_location_image.url at the returned URL as a separate, deliberate step.

multipart/form-data.

FieldTypeNotes
filefilerequiredThe PDF or image

{"kind": "brochures", "filename": "King_EV_MAX_2027.pdf",
 "size_bytes": 3215592, "url": "https://media.example.com/media/brochures/King_EV_MAX_2027.pdf"}

Rejected with 400 when

The extension is wrong for the kind · the file is empty or over the limit · the content doesn't match its type (leading bytes are checked, so a PDF renamed .jpg is refused) · the name already exists without overwrite=true.

Filenames are reduced to a single path component and the resolved parent is asserted, so an upload cannot write outside its directory. Writes are staged and then moved into place — the media host can never serve a half-uploaded file.

DELETE/admin/api/media/{kind}/{filename}
{"kind": "brochures", "filename": "King_EV_MAX_2026.pdf", "deleted": true}

404 for an unknown kind, or no such file.

Knowledge base

The documents Gemini File Search retrieves from when the bot answers a product question. The prompt tells the model to use only these — anything not indexed here, it cannot ground on.

Indexing has no upsert

Re-indexing a corrected document adds a second copy rather than replacing the first, and both stay retrievable — so the model may cite either. duplicate_display_names exists to make that visible, and replace=true on upload is how you avoid it.

Changes take effect on the next customer message. The store is resolved server-side per request, so there is nothing to restart.

POST/admin/api/kb

multipart/form-data.

FieldTypeNotes
filefilerequiredUp to 30 MB

curl -H "$AUTH" -F "file=@King_EV_MAX-English.pdf" "$BASE/admin/api/kb"

# re-index a corrected document without leaving the old one behind
curl -H "$AUTH" -F "file=@King_EV_MAX-English.pdf" -F "replace=true" \
  "$BASE/admin/api/kb"
{
  "display_name": "King_EV_MAX-English.pdf",
  "size_bytes": 3215592,
  "state": "STATE_PENDING",
  "indexing": true,
  "replaced_document_ids": ["oldid-abc123"]
}

This returns before the document is searchable. The upload takes seconds, indexing runs for minutes — holding the request open for the whole operation would be dropped by the tunnel in front of this app. Poll GET /admin/api/kb and wait for STATE_ACTIVE.

If replace was asked for but the cleanup failed, the upload still succeeds and replaced_document_ids comes back short — the new document is live, and the leftover is a duplicate to remove by hand.

Errors — 400 for an empty file, one over 30 MB, or a missing name. 502 when Gemini can't be reached, the API key is unset, or FILE_SEARCH_STORE is empty.

DELETE/admin/api/kb/{document_id}
{"document_id": "tvsthreewheelerskbpdf-qkm24fandaqq", "deleted": true}

404 if there is no such document in this store. The id is reduced to its last path segment and recombined with the configured store, so a full resource name pointing somewhere else cannot be used to reach another store's documents.

PUT/admin/api/config

Replaces the entire document. There is no partial update and no version history — always GET first, edit, then PUT back.

curl -s -H "$AUTH" "$BASE/admin/api/config" > cfg.json
# edit cfg.json
curl -s -X PUT -H "$AUTH" -H "Content-Type: application/json" \
  --data @cfg.json "$BASE/admin/api/config"

Returns the saved document on 200.

Required fields

bot_name · welcome_text · languages · capture_fields · flow_steps · voice_policy · campaign_text · intro

FieldRule

Product documents

documents replaces what used to be a hardcoded table, so a new model year is a config edit rather than a redeploy. brochure is the default; fuel overrides it when the customer names a fuel type; support PDFs are sent only when they ask about warranty or servicing — so asking for "the brochure" delivers one file, not three.

Removing a product stops the bot offering its brochure at all. If the key is absent, or the config can't be read, the built-in defaults apply — a config problem can never stop a customer getting a brochure.

Campaign scheduling

Both date fields are optional and default to null, meaning open-ended — a config with neither set behaves exactly as it did before scheduling existed. Bounds are inclusive and evaluated in India time, so a campaign ending 2026-10-31 stops after that day in IST rather than 5h30m out.

Outside the window the bot doesn't merely omit the offer: the CAMPAIGN section, the "make them aware of the active campaign" goal, and the campaign_awareness flow step are all removed from the prompt, and campaign_shown is instructed to stay empty. Leaving any one of them in was enough for the model to keep pitching a scheme that had expired.

FieldMeaning

sourceruntime (set through this API) · env (from .env) · null (none)

The key itself is never returned.

POST/admin/api/gemini
{"api_key": "AIza…"}

The key is validated with a live Gemini call before it is saved. On success it's written to data/gemini_key.txt (mode 600) and overrides the .env key; the worker picks it up on its next message. Returns the same shape as GET, with source now runtime.

Errors — 400 on a blank key, or {"detail": "Key rejected: …"} when Gemini refuses it. A rejected key is never saved, so a bad paste cannot take the bot down.

DELETE/admin/api/gemini

Removes the runtime key and falls back to .env. Returns the same shape as GET.

Check source first. If GEMINI_API_KEY is empty in .env, this leaves the bot with no key at all and it stops answering.

Building a client: the things that bite

Watch forWhy
Render leads from columnsAdmins can add and reorder capture fields at any time; a hard-coded column list goes stale silently
Group conversations by mobile, not sessionOne customer produces a fresh session every time their 1-hour window lapses
Encode + as %2BOtherwise it arrives as a space and the mobile filter matches nothing
count is the filtered totalPagination is Math.ceil(count / limit), not the length of items

Machine-readable spec

The OpenAPI 3.1 document is generated from the routes themselves, so it cannot drift from the code — a test fails if it goes stale. Import it straight into Postman, Insomnia, or a client generator.

# regenerate after changing a route
./venv/bin/python scripts/export_openapi.py

The same spec is served live at $BASE/openapi.json, with interactive views at $BASE/docs (Swagger) and $BASE/redoc. Swagger's Authorize button works — the spec declares an HTTPBearer scheme, so paste the token once and every "Try it out" carries it.
