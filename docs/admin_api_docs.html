How it fits together

A customer messages the dealership on WhatsApp. JAM's CRM receives it and forwards it to this system, which answers, captures a lead, and sends the reply back through the CRM. The admin API is a separate service alongside that pipeline — it reads and writes the same settings, database and Redis the bot uses, but it is never in the path of a customer message.

CustomerWhatsApp message
→
JAM CRMReceives and forwards; also delivers the reply
→
WebhookAccepts the message, puts it on the queue
→
QueueRedis — the buffer if traffic spikes
WorkerRuns the conversation, decides what to say
→
GeminiAnswers product questions from the knowledge base
→
StorageSession state in Redis; leads and transcripts on disk
→
Admin APIThis document. Reads and writes all of the above

What that means in practice

PropertyConsequence
No restartsSettings are re-read from disk on every customer message. A saved change reaches the bot on its next message — never mid-conversation, and never requiring a deploy.
Read-your-writesA PUT that returns 200 is already on disk. There is no propagation delay and no cache to bust.
Separate processThe admin API cannot see the worker directly. Everything it reports about the worker — liveness, queue depth — it learns through Redis.
Nothing here can break a live chatThe one exception is the settings themselves: a bad PUT changes what the bot says. Validation blocks the malformed cases, not the ill-advised ones.

One deliberate exception to "separate". Session reset writes into Redis, where the worker keeps live conversation state. That is the only endpoint that reaches into an in-flight conversation, and it is why it exists.

Base URL and authentication

Set these once and every example on this page runs as written.

# the admin host — currently a Cloudflare tunnel hostname
BASE=https://<your-admin-host>
AUTH="Authorization: Bearer $ADMIN_TOKEN"

Every endpoint requires the bearer header except the health probe and the panel pages. There is one shared token — no user accounts, no roles, no per-person access. Anyone holding it can read every customer's name, number and full chat history.

Authorization: Bearer <ADMIN_TOKEN>

Token comparison is constant-time, and a missing header is rejected identically to a wrong one — the endpoint gives a guesser nothing to work with.

Conventions

These hold across every endpoint, so they are stated once here rather than repeated below.

TopicRule
Format JSON in and out, UTF-8, except the two CSV exports and the file uploads, which are multipart/form-data. Send Content-Type: application/json on every body.
Timestamps Three shapes, and they differ: checked_at on status is UTC with a Z suffix; conversation timestamp is ISO 8601 with a +00:00 offset; lead timestamp has no offset — it is the server's local time as written to the CSV. Campaign dates are plain YYYY-MM-DD and are evaluated in India time.
Pagination limit and offset on the two list endpoints. limit defaults to 100 and is clamped to 1–500; offset clamps negatives to 0. count in the response is the total matching the filter, not the page size — so pages are Math.ceil(count / limit).
Phone numbers Stored and matched exactly as the CRM sends them, normally +91…. In a query string the + must be encoded as %2B or it arrives as a space and matches nothing.
Caching Only status caches: its outbound probes are held for 60 seconds so polling the page cannot hammer JAM's servers. A reused probe says so in its detail. Everything else reads live.
Rate limits None. The API is not public and is not throttled — but the knowledge-base endpoints call Gemini, which has its own quota.
Versioning The spec reports 1.0.0. There is no version in the URL and no negotiation; the OpenAPI document is generated from the routes, so it is always the truth about what is deployed.
Idempotency Every GET is safe. PUT /config is idempotent — sending the same document twice is the same as once. POST /kb is not: sending the same file twice indexes it twice (see replace).

Error responses

Every failure is a JSON body with a single detail string. There are no error codes to map and no nested error objects.

StatusMeansBody
400Validation failed — the message names the field{"detail": "<what was wrong>"}
401Header missing or wrong{"detail": "Invalid or missing admin token."}
404No such record, or not applicable{"detail": "…"}
502Gemini unreachable (knowledge base only){"detail": "…"}
503Redis unavailable (session reset only){"detail": "Redis unavailable: …"}
503ADMIN_TOKEN unset on the server{"detail": "Admin panel is disabled (ADMIN_TOKEN is not set)."}

An unset token disables the panel; it does not open it. Every request gets 503 until ADMIN_TOKEN is set — there is no state in which this API answers without one.

Common tasks

The jobs people actually arrive with, and the calls that do them. Every one assumes BASE and AUTH are set.

A customer says the bot told them something wrong
  1. Find the conversation. Search by their number — this covers every session they have ever had, not just the latest. 
    curl -s -H "$AUTH" "$BASE/admin/api/interactions?mobile=%2B919371062202"
  2. Read it in context. Take the session from the turn in question and pull the whole conversation. 
    curl -s -H "$AUTH" "$BASE/admin/api/interactions/client-e622c23876cc45a"
  3. Check what it was quoting. If the wrong answer was a product fact, look at what the bot is grounded on — a superseded document still in the store is the usual cause. 
    curl -s -H "$AUTH" "$BASE/admin/api/kb"
    Look at duplicate_display_names first. Anything listed there means two copies are live and the bot may have quoted the old one.
What did this number talk about three days ago?

There is no date filter on the API yet. Two ways round it, depending on volume:

  1. Small history — pull everything for the number and read the timestamp on each turn. Under a few hundred turns this is instant. 
    curl -s -H "$AUTH" \
  "$BASE/admin/api/interactions?mobile=%2B919371062202&limit=500"
  2. Large history — export to CSV and filter by date in a spreadsheet. 
    curl -s -H "$AUTH" -o cust.csv \
  "$BASE/admin/api/interactions/export.csv?mobile=%2B919371062202"

A date filter is a known gap and is on the list.

Change which brochure the bot sends for a model

Settings are replaced whole, so this is always read, edit, write back.

  1. Read the current settings. 
    curl -s -H "$AUTH" "$BASE/admin/api/config" > cfg.json
  2. Edit documents. Change brochure for the default, or a key under fuel to override it when the customer names a fuel type.
  3. Write it back. 
    curl -s -X PUT -H "$AUTH" -H "Content-Type: application/json" \
  --data @cfg.json "$BASE/admin/api/config"

The next customer to ask gets the new file. Nothing restarts.

Publish a brand-new brochure and point the bot at it

Two deliberate steps — uploading a file never changes what the bot sends, so a draft can be staged safely.

  1. Upload it and keep the url from the response. 
    curl -s -H "$AUTH" -F "file=@King_EV_MAX_2027.pdf" \
  "$BASE/admin/api/media/brochures"
  2. Point the settings at it — read /admin/api/config, paste the URL into documents, PUT it back.

Most product PDFs are hosted on JAM's own CDN rather than uploaded here. Either works — brochure takes any URL the bot can reach.

A campaign is ending — stop the bot promoting it
  1. Read the settings, set campaign_ends_on to the last valid day, PUT back.
  2. Nothing else to do. The bound is inclusive and evaluated in India time, so "2026-10-31" stops it after that day in IST.

Outside the window the campaign is not merely left unmentioned — the offer text, the goal, and the campaign step are all removed from the bot's instructions. Leaving any one of them in was enough for it to keep pitching an expired scheme.

Teach the bot about a new document
  1. Index it. Use replace=true when it supersedes an existing document with the same name. 
    curl -H "$AUTH" -F "file=@King_EV_MAX-English.pdf" \
  -F "display_name=King EV MAX specs" -F "replace=true" \
  "$BASE/admin/api/kb"
  2. Wait for it. The call returns in seconds but indexing takes minutes. Poll until the document reads STATE_ACTIVE. 
    curl -s -H "$AUTH" "$BASE/admin/api/kb"

Without replace=true you get two copies, both retrievable, and no way to tell which one the bot quoted. That is the single most common mistake with this API.

A customer is stuck mid-conversation
  1. Reset them by number. Their next message starts from language selection. 
    curl -s -X POST -H "$AUTH" -H "Content-Type: application/json" \
  -d '{"mobile":"+919371062202"}' "$BASE/admin/api/session/reset"

This clears language, captured answers, the confirmed dealer and which brochures were already sent. Their transcript and any captured lead are not deleted — this only clears live conversation state.

The bot has stopped replying
  1. Ask it what is wrong. 
    curl -s -H "$AUTH" "$BASE/admin/api/status"
  2. Read the six checks. Worker down means nothing is processing messages — they are queuing, not lost. Gemini key degraded means it cannot compose answers. JAM degraded means it cannot deliver them.
  3. If the key is the problem, confirm where it came from and rotate it. 
    curl -s -H "$AUTH" "$BASE/admin/api/gemini"

Operations

Is the bot alive, and how do I unstick one customer.

GET/admin/healthNo auth
What it does

Confirms the admin service itself is running and answering. Nothing more — it checks no dependency at all.

Use it when

Configuring an uptime monitor or a container health check. For "is the bot working", use status instead — this endpoint answers ok even when every dependency is down, and that is deliberate.

curl -s "$BASE/admin/health"

{"status": "ok"}
GET/admin/api/status
What it does

Runs six checks across everything the bot needs — Redis, the worker, the queue, the AI key and JAM's two endpoints — and rolls them into a single verdict.

Use it when

Somebody says "the bot isn't replying". This is the first thing to open, and usually the last: it distinguishes not processing from not composing from not delivering, which are three different problems with three different owners.

No parameters. Outbound probes are cached for 60 seconds, so polling this cannot hammer JAM's servers.

curl -s -H "$AUTH" "$BASE/admin/api/status"
{
  "status": "degraded",
  "checked_at": "2026-08-18T09:14:02Z",
  "checks": [
    {"name": "Redis",       "status": "ok",       "detail": "Connected (2 ms)"},
    {"name": "Worker",      "status": "ok",       "detail": "1 worker, last seen 4s ago"},
    {"name": "Queue",       "status": "degraded", "detail": "47 messages waiting, 3 failed"},
    {"name": "Gemini key",  "status": "ok",       "detail": "Runtime key active"},
    {"name": "JAM CRM",     "status": "ok",       "detail": "Reachable (310 ms)"},
    {"name": "JAM dispose", "status": "down",     "detail": "HTTP 502 (cached 12s ago)"}
  ]
}

Fields

FieldMeaning
statusok / degraded / down — the worst individual check
checked_atUTC, ISO 8601, Z suffix
checks[].nameFixed set — always these six, always this order, so a UI can lay them out statically
checks[].detailHuman-readable and safe to show as-is. Reused probes append (cached Ns ago)

What each check means, in plain terms

CheckWatchingIf it is bad
RedisThe shared memory holding live conversations and the queueNothing works. Everything below becomes unknowable
WorkerThe process that actually answers messagesMessages are queuing, not lost — they run when it returns
QueueHow many messages are waiting, and how many have failedA backlog means replies are slow; failures mean some never landed
Gemini keyWhether the bot can compose an answer at allIt can receive messages but cannot reply to product questions
JAM CRMCustomer lookupThe bot cannot tell who it is talking to
JAM disposeWhere qualified leads are postedConversations still work; leads are not reaching the CRM

Exact thresholds

Checkdowndegraded
Redisunreachable—
Workernone registeredheartbeat older than 480s
Queue—depth over ADMIN_QUEUE_WARN_DEPTH (default 20), or any failed jobs
Gemini key—not configured
JAM CRM / dispose—connection failure or 5xx

Absence is not a fault. A dependency that isn't configured reports ok with "Not configured". When Redis is down, Worker and Queue report down with "Unknown — Redis unreachable", because their true state cannot be known from here.

A 4xx from JAM counts as reachable. The check proves the host answers — not that the credentials are right.

POST/admin/api/session/reset
What it does

Erases one customer's remembered conversation state, so their next WhatsApp message starts over from language selection.

Use it when

Someone is stuck in a loop, picked the wrong language, wants to start again, or is testing and needs a clean run.

Clears language, captured answers, the confirmed dealer and which brochures were already sent. Their transcript and any captured lead survive — this only touches live state, not the record.

Request body

FieldTypeNotes
mobilestringrequiredNon-blank; whitespace trimmed. Use the format the CRM sends, normally +91…
 
curl -s -X POST -H "$AUTH" -H "Content-Type: application/json" \
  -d '{"mobile":"+919371062202"}' "$BASE/admin/api/session/reset"

{"mobile": "+919371062202", "cleared": true}

cleared is false when there was nothing to clear. Both are success — a customer with no live session is already in the state you asked for.

Deduplication keys are left alone; they are keyed per message, not per customer, so a reset cannot cause a replay.

Errors — 400 blank or missing mobile; 503 Redis unavailable.

Conversations

Every row is one turn — a single customer message or a single bot reply, not a whole conversation. Turns are written the moment they happen, so this is the authoritative record of what the bot actually said, independent of anything the model might report later.

GET/admin/api/interactions
What it does

Searches every message either side has ever sent — by phone number, by conversation, by language, by delivery status, or by phrase.

Use it when

A complaint arrives and you need to see what was actually said; you are checking whether a specific phrasing is going out; or you are working the queue of turns flagged for human review.

All parameters are optional and combine with AND.

needs_reviewbool—true = flagged and not yet reviewed; false = everything else

Field reference

FieldMeaning
idThe handle for marking a turn reviewed
roleuser or assistant. On a user turn, latency_ms, model, citations and the token counts are empty — they belong to the reply
statusok, or a failure such as delivery_failed when JAM would not accept the reply

count is the total matching the filter, not the page size. items is one page, ordered oldest first within the page, while pages walk backwards from the newest — so offset=0 is the most recent page and reads top-to-bottom like a transcript.

Examples

# everything this customer ever said, across all their sessions
curl -s -H "$AUTH" "$BASE/admin/api/interactions?mobile=%2B919371062202"

# what still needs a human
curl -s -H "$AUTH" "$BASE/admin/api/interactions?needs_review=true&limit=50"

# every reply JAM refused to deliver
curl -s -H "$AUTH" "$BASE/admin/api/interactions?status=delivery_failed"

# find a phrase
curl -s -H "$AUTH" "$BASE/admin/api/interactions?search=EMI"

Turns recorded before the mobile column shipped have mobile: "" and cannot be found by number. There is no backfill — for those, search by session or by phrase.

GET/admin/api/interactions/export.csv
What it does

Runs the same search and returns every match as a spreadsheet, with no page limit.

Use it when

Sharing with people who do not have panel access, doing bulk quality review, or filtering by date — which the API cannot do yet, but a spreadsheet can.

Accepts the same filters: mobile, session, channel, language, status, needs_review, search. Returns Content-Type: text/csv with Content-Disposition: attachment; filename="interactions.csv".

id,timestamp,session,mobile,channel,source,language,role,message,
latency_ms,status,error,model,citations,needs_review,reviewed_at,review_note

citations is a JSON array encoded as a string. The token-count columns are not in the export.

curl -s -H "$AUTH" -o interactions.csv \
  "$BASE/admin/api/interactions/export.csv?mobile=%2B919371062202"

This file is customer data. Names, numbers and everything said. Treat the download the way you would treat the CRM itself.

GET/admin/api/interactions/{session}
What it does

Returns one conversation start to finish, oldest turn first, up to 500 turns.

Use it when

You have found a single turn through search and need the surrounding context — what was asked just before, and what the bot said next.

curl -s -H "$AUTH" "$BASE/admin/api/interactions/client-e622c23876cc45a"

{
  "session": "client-e622c23876cc45a",
  "count": 12,
  "items": [ /* same shape as the search endpoint */ ]
}

404 when the session has no turns.

A session is not a customer. Conversation state expires after an hour of silence, and a customer who comes back gets a brand-new session id. One person who messages across three days will have three or more sessions. To see everything they ever said, search by mobile.

POST/admin/api/interactions/{id}/review
What it does

Closes one flagged turn, optionally recording what was done about it.

Use it when

Working through the turns the bot flagged for a human, so the same item is not handled twice by two people.

{id} is the numeric id from the search endpoint. The body is optional — {} is valid.

FieldTypeNotes
notestringoptionalTrimmed. Defaults to ""
 
curl -s -X POST -H "$AUTH" -H "Content-Type: application/json" \
  -d '{"note":"dealer called back"}' "$BASE/admin/api/interactions/4101/review"

{"id": 4101, "reviewed": true, "note": "dealer called back"}

404 here is normal, not an error to surface loudly. It means the turn is not awaiting review — either it was never flagged, or somebody already claimed it. That is deliberate: it is what stops two people working the same item.

Leads

What the bot captured, as opposed to what it said. One row per qualified customer, read under a shared file lock so a page is never a half-written file.

Media

Files the bot sends to customers on WhatsApp. data/media is a shared volume: the admin service writes to it, and the media host serves the same directory read-only. Publishing is therefore a file write — no CDN account, no third party, no long-running job.

The two kinds

kindDirectoryAcceptsLimitUsed for
brochuresdata/media/brochures.pdf25 MBProduct brochures, warranty and service-schedule PDFs
imagesdata/media/share_location.jpg .jpeg .png5 MBThe how-to-share-your-location cards sent to customers who do not know their pincode

Any other {kind} returns 404.

Uploading does not change what the bot sends. Publishing a draft must never start delivering it — so pointing the settings at a new file is always a separate, deliberate second step.

GET/admin/api/media/{kind}
What it does

Lists what is already published for that kind, with each file's public URL and size, plus the limits the upload endpoint will enforce.

Use it when

Before uploading — to check a name is free and see the size limit — or to copy a URL to paste into the settings.

{
  "kind": "brochures",
  "base_url": "https://media.example.com/media/brochures",
  "max_upload_bytes": 26214400,
  "allowed_suffixes": [".pdf"],
  "items": [
    {"filename": "King_EV_MAX_2027.pdf", "size_bytes": 3215592,
     "url": "https://media.example.com/media/brochures/King_EV_MAX_2027.pdf"}
  ]
}

max_upload_bytes and allowed_suffixes come from the server, so a form can validate before uploading rather than after.

POST/admin/api/media/{kind}
What it does

Publishes a file to the media host and returns the URL it is now reachable at.

Use it when

A new model-year brochure arrives, or a share-location card needs replacing — and you do not want to wait on someone else's CDN to host it.

multipart/form-data.

FieldTypeNotes
filefilerequiredThe PDF or image
overwritebooloptionalDefaults false — replacing an existing name has to be deliberate
 
curl -s -H "$AUTH" -F "file=@King_EV_MAX_2027.pdf" \
  "$BASE/admin/api/media/brochures"

curl -s -H "$AUTH" -F "file=@how_to.jpg" \
  "$BASE/admin/api/media/images"

{"kind": "brochures", "filename": "King_EV_MAX_2027.pdf",
 "size_bytes": 3215592, "url": "https://media.example.com/media/brochures/King_EV_MAX_2027.pdf"}

Rejected with 400 when

The extension is wrong for the kind · the file is empty or over the limit · the content does not match its type (the leading bytes are checked, so a PDF renamed .jpg is refused) · the name already exists and overwrite=true was not sent.

Filenames are reduced to a single path component and the resolved parent directory is asserted, so an upload cannot write outside its own directory. Writes are staged and then moved into place atomically — the media host can never serve a half-uploaded file.

DELETE/admin/api/media/{kind}/{filename}
What it does

Removes one published file from the media host.

Use it when

Retiring a superseded document, or clearing a bad upload.

{"kind": "brochures", "filename": "King_EV_MAX_2026.pdf", "deleted": true}

404 for an unknown kind, or no such file.

Check the settings first. Deleting a file the settings still point at does not fail here — it fails later, silently, when a customer asks for that brochure and the send has nothing to attach. Update documents before deleting, not after.

Knowledge base

The documents the bot's product answers are grounded in. When a customer asks about specs, pricing, warranty or service, the bot searches these files and answers from what it finds. The prompt instructs it to use only these — anything not indexed here, it cannot ground on.

The one thing to understand: indexing has no upsert

Re-indexing a corrected document adds a second copy rather than replacing the first, and both stay retrievable — so the bot may quote either, with nothing in the answer to say which. duplicate_display_names exists to make that visible, and replace=true on upload is how you avoid creating it.

Changes take effect on the next customer message. The store is resolved per request, so there is nothing to restart and no cache to clear.

What it does

Lists every document the bot can currently quote from, newest first, and flags any name that appears more than once.

Answering "why did the bot say that" — a stale duplicate is the usual culprit — or confirming that a document you just uploaded has finished indexing.

What it does

  "$BASE/admin/api/kb"
{
  "display_name": "King_EV_MAX-English.pdf",
  "size_bytes": 3215592,
  "state": "STATE_PENDING",
  "indexing": true,
  "replaced_document_ids": ["oldid-abc123"]
}

This returns before the document is searchable. The upload takes seconds; indexing runs for minutes. Holding the request open for the whole operation would be dropped by the tunnel in front of this service, so it returns early by design. Poll GET /admin/api/kb and wait for STATE_ACTIVE.

If replace was asked for but the cleanup failed, the upload still succeeds and replaced_document_ids comes back short — the new document is live, and the leftover is a duplicate to remove by hand. The order is deliberate: deleting first would leave the bot with no source at all if the upload then failed.

Errors — 400 for an empty file, one over 30 MB, or a missing name. 502 when Gemini cannot be reached, the API key is unset, or no store is configured.

Configuration

Everything about how the bot behaves that is not code: what it is called, which questions it asks, which brochures it sends, and which campaign it promotes. Read it, edit it, write the whole document back — changes reach the bot on its next message, with no restart.

PUT/admin/api/config
What it does

Saves the settings. Replaces the entire document — there is no partial update.

Use it when

Changing campaign dates, swapping a brochure URL, adding a capture field, or reordering the conversation.

Always read, edit, write back. There is no version history, so a blind write loses whatever another admin saved in the meantime.

curl -s -H "$AUTH" "$BASE/admin/api/config" > cfg.json
# edit cfg.json
curl -s -X PUT -H "$AUTH" -H "Content-Type: application/json" \
  --data @cfg.json "$BASE/admin/api/config"

Returns the saved document on 200.

Required fields

bot_name · welcome_text · languages · capture_fields · flow_steps · voice_policy · campaign_text · intro

FieldRule

Product documents

documents replaces what used to be a hardcoded table, so a new model year is a settings edit rather than a software release. brochure is the default; fuel overrides it when the customer names a fuel type; support PDFs are sent only when they ask about warranty or servicing — so asking for "the brochure" delivers one file, not three.

Removing a product stops the bot offering its brochure at all. If the key is absent, or the settings cannot be read, built-in defaults apply — a settings problem can never stop a customer getting a brochure.

Campaign scheduling

Both dates are optional and default to null, meaning open-ended — a configuration with neither set behaves exactly as it did before scheduling existed. Bounds are inclusive and evaluated in India time, so a campaign ending 2026-10-31 stops after that day in IST rather than five and a half hours out.

Outside the window the bot does not merely omit the offer: the campaign section, the "make them aware of the active campaign" goal, and the campaign step are all removed from its instructions, and it is told to record no campaign as shown. Leaving any one of them in was enough for it to keep pitching a scheme that had expired.

POST/admin/api/gemini
What it does

Sets or rotates the AI key — testing it against Gemini before saving it.

Use it when

A key has expired, hit its quota, or needs rotating, and you would rather not redeploy to change it.

{"api_key": "AIza…"}

The key is validated with a live Gemini call before it is saved. On success it is written to the server with restricted permissions and overrides the deployed key; the bot picks it up on its next message. Returns the same shape as GET, with source now runtime.

Errors — 400 on a blank key, or {"detail": "Key rejected: …"} when Gemini refuses it. A rejected key is never saved, so a mistyped paste cannot take the bot down.

DELETE/admin/api/gemini
What it does

Removes the runtime key, falling back to whatever key the deployment carries.

Use it when

Undoing a temporary key — reverting to the one managed with the deployment.

Returns the same shape as GET.

Check source first. If the deployment has no key of its own, this leaves the bot with nothing and it stops answering product questions immediately.

Glossary

Terms that appear in responses and mean something specific here.

turn
One message in one direction — either a customer message or a bot reply. The unit every conversation endpoint returns.
session
One continuous conversation. State expires after an hour of silence, so one customer has many sessions over time. Never treat a session id as a person.
mobile
The customer's phone number, exactly as JAM's CRM sends it. The only stable identifier for a person across sessions.
lead
A row of details the bot captured during a conversation. Written to a file separate from the transcript, and posted to the CRM.
disposition
The outcome the bot assigned to a conversation, posted to JAM's CRM — how the lead is classified for follow-up.
capture field
A detail the bot is configured to collect. Adding one changes both what the bot asks and the columns in the leads file.
flow step
One stage of the scripted conversation order, e.g. model_interest or timeline.
campaign
The scheme the bot promotes, with an optional start and end date. Outside those dates it is stripped from the bot's instructions entirely.
knowledge base
The set of documents the bot's product answers are grounded in. Also called the store.
display name
A document's human-readable name in the knowledge base. Two documents sharing one is what duplicate_display_names reports.
runtime key
A Gemini API key set through this API and stored on the server, overriding the one deployed with the code.
kind
Which media directory an upload belongs to — brochures or images. Each has its own file types and size limit.
worker
The background process that actually runs conversations. Separate from this API, which only observes it through Redis.
queue
Messages accepted but not yet answered. A backlog means slow replies, not lost ones.

Building a client: the things that bite

Each of these is a bug somebody writes before they read the prose explaining it.

Watch forWhy
Render leads from columnsAdmins can add and reorder capture fields at any time; a hard-coded column list goes stale silently
Group conversations by mobile, not sessionOne customer produces a fresh session every time their hour of silence lapses
Encode + as %2BOtherwise it arrives as a space and the mobile filter matches nothing — silently, with a 200 and an empty list
count is the filtered totalPagination is Math.ceil(count / limit), not the length of items

Machine-readable spec

The OpenAPI 3.1 document is generated from the routes themselves, so it cannot drift from the code — a test fails if it goes stale. Import it straight into Postman, Insomnia, or a client generator.

# regenerate after changing a route
./venv/bin/python scripts/export_openapi.py

The same spec is served live at $BASE/openapi.json, with interactive views at $BASE/docs (Swagger) and $BASE/redoc. Swagger's Authorize button works — the spec declares a bearer scheme, so paste the token once and every "Try it out" carries it.
